GENERAL ACTION EXECUTION ENGINE
for Android AI — Elderly & Accessibility Focus
Technical Proposal & Build Roadmap  •  2026
Executive Summary
This document proposes a General Action Execution Engine (GAEE) — a universal AI brain layer for Android that lets users control their phone through natural conversation, with zero code written per task. The engine understands intent, decomposes it into steps, executes those steps across any app, and learns from every interaction so it gets faster over time.
🎯  Core Promise
The user says what they want in plain language. The AI figures out how to do it, executes it across any app on the phone, and remembers it for next time. No app-specific integrations. No programming. No hardcoded commands.
The initial target market is elderly users (60+) and their families — a segment that is massively underserved by current AI assistants, growing rapidly, and impossible for Google to serve with the depth required.

Smartphones were designed by young engineers for young users. The result is a daily experience of frustration, embarrassment, and dependence for hundreds of millions of elderly people worldwide.

Why Google Will Not Solve This
Google's Gemini Intelligence is a general-purpose agent for a billion users. That design constraint makes it impossible for them to go deep on any specific group. Specifically:
Gemini assumes you know how to prompt it — elderly users do not
It has no family oversight layer — a critical feature for this market
It optimises for breadth of tasks, not depth of trust with one user profile
Google cannot afford the liability of making irreversible actions on behalf of vulnerable users without the confirmation-first design this segment requires
Model Strategy — Works on Every Phone
One of the core promises of GAEE is that it works for any elderly user regardless of what phone they own. A user with a brand new Samsung S24 and a user with a 6-year-old budget Android should both be able to use the app on day one. This is achieved through a three-tier model strategy that detects capability at first launch and silently adapts.

The General Action Execution Engine (GAEE)
The key insight of GAEE is that you do not code for every task. Instead, you build five generic layers that together can handle any task on any app — including apps that do not have an API.
Layer 1 — Intent Understanding
The engine's entry point. Converts any natural language command into a structured, machine-readable intent object.
Component
What It Does
Voice transcription
Converts speech to text on-device using Whisper (tiny model, runs locally, no cloud needed)
Intent classifier
Gemini Nano (if pre-installed by Google on the phone) OR Claude API over internet (for all other phones). Either way outputs the same structured result: intent type, complexity score, extracted arguments. No model is downloaded.
Ambiguity resolver
If confidence is below threshold, asks one clarifying question in simple plain English before proceeding
Safety gate
Flags irreversible actions (calls, purchases, deletions) and routes them through a confirmation step before execution
💡  Example
"Send a photo to my daughter Maria" → { intent: "send_media", app: "whatsapp", contact: "Maria", media_type: "photo", confirmation_required: true }
Layer 2 — Action Cache (The "No-Code" Engine)
The cache is what makes this engine truly general. The first time any task runs, the AI reasons through it from scratch. Every subsequent time, it reuses the cached plan — no AI inference needed, sub-100ms execution.

How the cache lookup works
User command is converted to a 384-dimensional vector using an on-device sentence embedding model (all-MiniLM-L6-v2, ~80MB)
Cosine similarity is computed against all cached entry embeddings
If best match exceeds 0.78 similarity threshold → cache hit, extract args and execute immediately
If no match → route to LLM to reason a new plan, then write the successful plan back to cache
Cache grows itself over time. After ~2 weeks of use, >90% of everyday tasks are cache hits
⚡  Performance impact
Cache hit: 50–150ms total execution start. Cache miss (LLM reasoning): 1–4 seconds. After one month of use, a typical elderly user's top 20 daily tasks are all cache hits.
Layer 3 — Action Planner
Converts the intent + args into a concrete, ordered sequence of tool calls. This is where "set an alarm for 7am" becomes specific Android API calls. The planner never hardcodes task logic — it uses a library of generic tools and lets the LLM (or cache) decide how to combine them.

🔑  How tier selection works
On first launch, the app silently checks if Gemini Nano is available. If yes → Tier 1, done. If no → show a single friendly plain-English dialog asking permission to use the cloud. If user agrees → Tier 2. If user declines → Tier 3. This decision is stored and never asked again. If the phone is offline and Tier 2 is selected, it automatically falls back to Tier 3 for that session.
For complex tasks (trip planning, research, multi-step reasoning) all tiers route to the large cloud model regardless — this runs at night when the phone is on charge, via WorkManager. Tier only affects the intent classification step, not the execution of heavy tasks.
Layer 5 — Execution & Learning Loop
After the action plan runs, the engine closes the loop: it checks if the task succeeded, speaks the result to the user, writes to cache, and adjusts future behaviour.
Execute each step in the action plan sequentially using the tool library
After each step, verify success by reading the screen state (ScreenReader tool)
If a step fails, retry once with a modified approach, then ask the user to take over
Speak the result in simple plain English ("Done! I sent your photo to Maria.")
Write the successful plan + outcome to cache with updated hit_count and success_rate
If the user corrects the engine ("No, I meant Maria Rodriguez not Maria Smith"), update the contact resolution preference and store the correction
Weekly: large model reviews all low-success-rate cache entries and proposes improved plans
Elderly-First Design Decisions
The engine is general-purpose, but these design choices make it specifically right for elderly users. None of these are available in Google Gemini or Siri.
1. Confirmation Before Everything Risky
Any action classified as irreversible (call, purchase, delete, send message) triggers a large-button confirmation dialog spoken aloud before execution. The user can say "yes", "no", or "wait" at any point.
2. Family Dashboard
Adult children get a companion app showing:
What tasks their parent attempted this week and whether they succeeded
Which contacts are marked as trusted (calls from others are flagged)
Ability to pre-configure shortcuts: "When Dad says 'call the doctor', always call Dr. Patel at 555-0192"
Scam alert log: calls and messages the engine flagged as suspicious
This is a critical insight: the paying customer is often the adult child, not the elderly parent. The family dashboard is your primary sales and retention tool.
3. Plain English Everything
The TTS engine is configured to speak at 0.85x speed, use simple vocabulary, and always confirm what it just did. No technical jargon, no error codes. If something fails, it says "I couldn't do that — would you like me to try again or call Maria for help?"
4. Teach Mode
If the engine cannot figure out a task, it enters teach mode: it asks the user to show it once while it watches using the ScreenReader. It records the sequence of taps and writes a new cache entry. Next time, it does it automatically.
5. Scam Detection
The NotificationReader and call handler run every incoming call and message through a lightweight classifier checking for:
Unknown numbers claiming to be known people
Urgency language ("act now", "your account will be closed")
Requests for money, gift cards, or personal information
Mismatched caller ID vs. speech content
If flagged, the engine speaks a quiet alert to the user: "This might be a scam. Want me to hang up and call your daughter to check?"

What You Explicitly Do Not Build
🚫  The hardcoding trap
The most common mistake when building AI assistants is writing specific code for every task. "If the user says alarm, call AlarmManager. If the user says WhatsApp, launch com.whatsapp." This creates a system that has 50 commands on day one and stops growing. GAEE is designed to never fall into this trap.
You do not build:
A handler for "set alarm" — the cache and UINavigator handle it
A handler for "open WhatsApp" — AppLauncher + UINavigator handle it
A DoorDash integration — UINavigator navigates DoorDash like a human would
A YouTube integration — UINavigator + MediaController handle it
An Uber integration — WebFetcher calls Uber's API, or UINavigator uses the app
A per-city travel planner — the large model generates the plan from scratch each time
You build once:
The generic tool library (~15 tools covering all interaction types)
The cache lookup and write pipeline
The intent classifier prompt
The action planner that combines tools into plans
The confirmation and safety layer
Everything else the LLM figures out, caches, and reuses.

The Intent Classifier — Exact Prompt
This is the most important part of Phase 1. The coding Claude must use this prompt exactly as written for the LLM call. Do not paraphrase it.
SYSTEM PROMPT:
You are an intent classifier for an Android phone assistant designed for elderly users.
The user will speak a command in natural language. Your job is to classify it.
You must respond with ONLY a valid JSON object. No explanation. No markdown. No extra text.
JSON format:
{
"intent": "<intent_name>",
"confidence": <0.0 to 1.0>,
"args": { <key>: <value> },
"confirmation_required": <true|false>,
"speak_before": "<what to say to user before confirming>",
"unknown": <true|false>
}
Valid intents and their args:
set_alarm        → args: { time: "HH:MM", label: "string or null" }
set_reminder     → args: { time: "HH:MM", message: "string" }
call_contact     → args: { name: "string" }
send_sms         → args: { name: "string", message: "string" }
open_app         → args: { app_name: "string" }
get_weather      → args: {}
set_volume       → args: { direction: "up|down", level: 0-100 or null }
toggle_wifi      → args: { state: "on|off" }
open_camera      → args: {}
Rules:
- confirmation_required must be true for: call_contact, send_sms
- confirmation_required is false for: set_alarm, set_reminder, get_weather, set_volume, toggle_wifi, open_app, open_camera
- If you cannot match any intent with confidence >= 0.6, set unknown: true and intent: "unknown"
- speak_before must be simple plain English an elderly person can understand
- speak_before example for call_contact: "I will call Maria now. Is that okay?"
- speak_before example for set_alarm: "Setting your alarm for 7am."

Model Strategy — Three-Tier Fallback
The app must work on any Android phone regardless of age or specs. The coding Claude must implement a three-tier fallback chain. The phone automatically detects which tier it can support and uses the best available option. The user never sees technical details — they only see a one-time setup prompt if cloud is needed.
🔑  Core principle
Every tier produces the same IntentResult data class. The rest of the engine — ActionPlanner, ExecutionEngine, all tools — never knows or cares which tier handled classification. The tier is an implementation detail completely hidden inside IntentClassifier.kt.
Tier 1 — On-Device Model (Best, used when available)
Requires: Pixel 6+ or Samsung S21+ or any device with 6GB+ RAM and Android 10+.
Use Gemini Nano via Android ML Kit AIManager API
Completely free, zero latency, works fully offline, data never leaves the device
On app first launch, call AIManager.isAvailable(). If true, Gemini Nano is already on the phone — use it. If false, go to Tier 2. No download happens in either case.
No user prompt needed — just silently use it
Tier 2 — Cloud API (Fallback for older phones, requires internet)
Used when: device does not support Gemini Nano. Requires internet connection.
On first launch, if Tier 1 unavailable, show a single friendly one-time dialog (see exact wording below)
If user agrees, store cloudEnabled = true in SharedPreferences and proceed
If user declines, fall through to Tier 3
For classification calls: send transcript to Claude API (claude-haiku-3-5 — fastest and cheapest) with the intent classifier prompt
Cost: approximately $0.0003 per classification call — negligible for daily use
Add INTERNET permission check before every cloud call. If offline, fall through to Tier 3 automatically
Show a small subtle indicator in the status text: "Using cloud" — not alarming, just honest
Tier 3 — Keyword Classifier (Last resort, always works, no internet needed)
Used when: Tier 1 unavailable AND (user declined cloud OR no internet connection). Handles the 10 Phase 1 tasks only.
Pure string matching on the transcript — no model, no network, instant
"alarm" or "wake me" → set_alarm
"remind" → set_reminder
"call" → call_contact
"message" or "text" or "send" → send_sms
"weather" or "temperature" → get_weather
"volume" or "louder" or "quieter" → set_volume
"wifi" or "wi-fi" → toggle_wifi
"camera" or "photo" → open_camera
No match found → open_app (pass full transcript as app_name, let AppLauncherTool fuzzy-match it)

ModelTier Enum and Detection Logic
IntentClassifier.kt must implement this detection flow on every cold start:
// ModelTier.kt
enum class ModelTier { ON_DEVICE, CLOUD, KEYWORD }
// Inside IntentClassifier.kt — called once at startup
suspend fun detectAndStoreTier(context: Context): ModelTier {
val prefs = context.getSharedPreferences("gaee", Context.MODE_PRIVATE)
// Tier 1: on-device model available?
val aiAvailable = AIManager.getInstance(context).isAvailable()
if (aiAvailable) {
prefs.edit().putString("model_tier", "ON_DEVICE").apply()
return ModelTier.ON_DEVICE
}
// Tier 2: cloud previously approved?
if (prefs.getBoolean("cloud_enabled", false)) {
return ModelTier.CLOUD
}
// Tier 2: ask user (first time only)
val userApproved = showCloudPermissionDialog(context)
if (userApproved) {
prefs.edit().putBoolean("cloud_enabled", true).apply()
return ModelTier.CLOUD
}
// Tier 3: keyword fallback
return ModelTier.KEYWORD
}
// classify() — called on every voice command
suspend fun classify(transcript: String): IntentResult {
val hasInternet = isNetworkAvailable(context)
return when {
tier == ModelTier.ON_DEVICE -> classifyOnDevice(transcript)
tier == ModelTier.CLOUD && hasInternet -> classifyCloud(transcript)
else -> classifyKeywords(transcript)  // Tier 3 or offline fallback
}
}
